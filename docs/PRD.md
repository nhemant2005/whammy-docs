# WhammyDocs — Updated PRD

## Problem Statement

Developers hate writing documentation. After building a project, the last thing anyone wants to do is manually write READMEs, API references, architecture overviews, and setup guides. As a result, most projects have outdated, incomplete, or nonexistent docs — causing onboarding confusion, API misuse, and wasted engineering time.

Current solutions require manual effort (writing markdown by hand) or complex static site generators with steep learning curves. There is no fast, AI-powered way to drop in a codebase and get polished, editable documentation in seconds.

## Solution

WhammyDocs is a web-based tool where a developer uploads their project folder as a `.zip`, optionally describes what it does, and receives a complete documentation website — README, API reference, architecture overview, and guides — generated by AI with token-level streaming so they can watch it being written in real time.

The user can preview, edit sections inline, and selectively regenerate individual sections before downloading the final output as a ready-to-host MkDocs site.

## User Stories

### Upload & Configuration

1. As a developer, I want to upload my project as a `.zip` file via a drag-and-drop zone, so that I don't need any CLI tools or setup to get started.
2. As a developer, I want to select between Quick mode (README + API ref) and Comprehensive mode (all five sections), so that I can control how deep the analysis goes.
3. As a developer, I want to see an inline error message immediately if my file exceeds 50MB, so that I don't wait for a failed upload.
4. As a developer, I want to see an inline error message if I upload a non-`.zip` file, so that I understand the format requirement without reading documentation.
5. As a developer, I want my upload to be validated for both file type and size before it reaches the server, so that feedback is instant.
6. As a developer, I want a "Try with sample project" button on the upload page, so that I can see a real end-to-end generation before committing my own code.
7. As a developer, I want the sample project demo to run the live AI pipeline (not pre-baked output), so that the demo is a genuine demonstration of the product.

### Generation & Progress

8. As a developer, I want to see a real-time progress screen after uploading, so that I know the system is working and how far along it is.
9. As a developer, I want to see which section is currently being generated (e.g., "Generating API Reference..."), so that I understand what is happening at each moment.
10. As a developer, I want to watch the AI write each documentation section token-by-token, so that the generation feels alive and transparent rather than a black box.
11. As a developer, I want each documentation section to appear and fill in sequentially (not all at once), so that I can read earlier sections while later ones generate.
12. As a developer, I want the generation to use only the files most relevant to each section (not the entire codebase), so that each section is accurate and token costs stay low.
13. As a developer, I want large files to be summarised (signatures + docstrings) rather than sent in full, so that generation works correctly on larger projects without hitting context limits.
14. As a developer, I want binary files, lock files, build artifacts, and dependency folders to be automatically excluded, so that I don't have to clean my project before uploading.
15. As a developer, I want Comprehensive mode to generate README, API Reference, Architecture Overview, Getting Started, and Deployment sections, so that I get a complete documentation suite.
16. As a developer, I want Quick mode to generate only README and API Reference, so that I can get useful output in under 20 seconds for smaller projects.
17. As a developer, I want the AI to infer my project's language and framework from the code itself (not require me to specify it), so that upload is frictionless.
18. As a developer, I want to see a clear error state if the AI generation fails mid-way, so that I can retry without refreshing and losing context.

### Preview & Editing

19. As a developer, I want to see all generated sections rendered as formatted HTML in a preview page, so that I can judge the quality of the output immediately.
20. As a developer, I want each section rendered from markdown to HTML using a client-side renderer, so that the preview matches the final output.
21. As a developer, I want to click Edit on any section to open it as a plain text area containing raw markdown, so that I can make precise corrections.
22. As a developer, I want to click Save to persist my edits to the server, so that my changes are preserved across regenerations and download.
23. As a developer, I want edited sections to not be overwritten when I regenerate a different section, so that my manual corrections are respected.
24. As a developer, I want to click "Regenerate with AI" on any individual section, so that I can fix a poor section without re-processing the entire project.
25. As a developer, I want section regeneration to stream tokens in real time into just that section card, so that the experience is consistent with initial generation.
26. As a developer, I want section regeneration to use only the source files mapped to that section, so that the call is fast and focused.
27. As a developer, I want a visual indicator when a section has unsaved edits, so that I don't accidentally download without saving my changes.
28. As a developer, I want the preview page to load immediately after generation completes, so that there is no additional wait before I can start editing.

### Download & Output

29. As a developer, I want to download a `.zip` file containing the fully built MkDocs HTML site, so that I can host the documentation anywhere without installing anything locally.
30. As a developer, I want the downloaded zip to also include the raw markdown source files, so that I can continue editing the docs in any text editor.
31. As a developer, I want the MkDocs output to use the Material theme with dark/light toggle and search, so that the documentation looks professional out of the box.
32. As a developer, I want the MkDocs navigation to be generated automatically from the sections I have, so that I don't need to configure anything before the docs are usable.

### Session & State

33. As a developer, I want my session (uploaded files, generated docs, edits) to persist for the duration of my working session without requiring a login, so that I can work without an account.
34. As a developer, I want my session to be isolated from other users' sessions, so that concurrent uploads don't interfere with each other.

## Implementation Decisions

### Session State

- Each upload generates a UUID `session_id`. All session data lives under `/tmp/whammy-<session_id>/`: extracted source files, generated markdown files, `mapping.json`, generated `mkdocs.yml`, and the built `site/` folder.
- `session_id` is passed as a hidden field in every subsequent HTMX request and SSE connection.
- No database. No Redis. The section→file mapping is stored as `mapping.json` within the session folder — co-located with the files it references.
- Rationale: the data is inseparable from the files already on disk; a database would create two things to keep in sync and clean up. For a single-VPS, pre-recorded demo deployment, temp files are the correct choice.

### File Upload

- `POST /upload` receives `UploadFile` via FastAPI.
- Size validation: 50MB hard cap enforced at both browser (JS check before submit) and FastAPI layer (check before writing to disk). Error returned as an inline message on the upload form, not a full error page.
- File type validation: `.zip` only, enforced at both layers.
- Extraction: Python `zipfile` module, wrapped in `try/except` to handle corrupted or password-protected archives gracefully.
- After extraction: run the file scanner, generate `mapping.json`, then redirect to the streaming generation page.

### File Scanner & Section→File Mapping

- Universal ignore list applied to all projects regardless of language: `node_modules/`, `__pycache__/`, `.git/`, `venv/`, `env/`, `dist/`, `build/`, `*.pyc`, `*.class`, `*.lock`, `package-lock.json`, `yarn.lock`, `Pipfile.lock`, and binary files (detected by attempting UTF-8 decode).
- No explicit language detection. The LLM infers language from code content. Path-based pattern matching is used for section→file mapping:
  - **API Reference** → files under `routes/`, `controllers/`, `api/`, `views/`; filenames matching `*router*`, `*endpoint*`, `*handler*`
  - **Getting Started** → `requirements.txt`, `package.json`, `Pipfile`, `go.mod`, `*.env.example`, top-level `README*`
  - **Deployment** → `Dockerfile`, `docker-compose*`, `.github/workflows/`, `nginx.conf`, `*.yml` in root
  - **Architecture** → directory tree only (no file content)
  - **README** → top-level files + detected entry point
- Mapping saved to `mapping.json`.

### Skeleton Extraction

Tiered by file size to stay within context limits without silent truncation:

| File size | What is sent to the LLM |
|---|---|
| < 5KB | Full file content |
| 5KB – 20KB | Function/class signatures + docstrings only |
| > 20KB | Filename + first 30 lines |

For Python: extract using regex on `def`, `class`, and docstring patterns. For JS/TS: exported functions, classes, and interface declarations. For all others: first 30 lines.

The LLM prompt notes when content has been skeletonised so it can calibrate its confidence.

### AI Pipeline — DeepSeek Streaming

- One DeepSeek API call per section using the OpenAI-compatible endpoint (`httpx` async client, `stream=True`).
- Sections are generated sequentially, not in parallel, so the SSE stream has a natural section-by-section flow.
- Each section uses a focused, section-specific prompt. Prompt quality is the primary lever for output quality — each prompt specifies output format explicitly (markdown, no preamble, start with content directly).
- 5 sections for Comprehensive (README → API Reference → Architecture → Getting Started → Deployment), 2 for Quick (README → API Reference).
- API key stored as environment variable `DEEPSEEK_API_KEY`, loaded via `python-dotenv`.

### SSE Streaming Architecture

- `GET /stream/<session_id>` returns a `StreamingResponse` with `media_type="text/event-stream"`.
- An async generator drives the stream: for each section, emit a `section-start` named event, then pipe DeepSeek token chunks as `data:` events, then emit a `section-complete` named event.
- Frontend uses HTMX SSE extension (`hx-ext="sse"`, `sse-connect`, `sse-swap`) to append tokens to the active section card in real time.
- Section cards have stable IDs (`section-readme`, `section-api-reference`, etc.) for HTMX targeting.
- After all sections complete, a final `event: building` event triggers the MkDocs build on the server and shows a "Building site..." indicator.

### Edit & Save Flow

- [Edit] replaces the rendered section card with a `<textarea>` containing raw markdown (simpler than `contenteditable`).
- [Save] sends `POST /edit` with `session_id`, `section`, and `content`. Server writes to the section's markdown file. Returns an HTML fragment; HTMX swaps only that card (`hx-target="#section-<name>"`, `hx-swap="outerHTML"`).
- No auto-save on keystroke — explicit Save click only. This is intentional: user confirms their edit.
- Unsaved edits indicator shown on the card after any change.

### Regenerate Flow

- [Regenerate with AI] sends `POST /regenerate` with `session_id` and `section`. Server returns a new SSE stream URL scoped to that section.
- Frontend opens a new SSE connection targeted only at `#section-<name>`. Other cards are untouched.
- Server reads `mapping.json` → fetches only that section's source files → calls DeepSeek with streaming → pipes tokens through SSE.
- On completion, server writes the new content to the markdown file.

### MkDocs Build

- After all sections stream, server generates `mkdocs.yml` from a template (site name, Material theme, nav structure matching the generated sections).
- Runs `subprocess.run(["mkdocs", "build", "--config-file", f"/tmp/whammy-{session_id}/mkdocs.yml"])`.
- MkDocs + Material theme pre-installed on VPS as part of Python dependencies.
- Build errors surfaced to the user with a retry option.

### Download

- `GET /download/<session_id>` zips the `site/` folder and raw markdown files into a single archive.
- Returned as `FileResponse` with `Content-Disposition: attachment; filename="whammy-docs.zip"`.

### Deployment

- Develop locally → push to GitHub (`whammy-docs`) → SSH into VPS → `git pull` → restart uvicorn.
- VPS is user-owned. No nginx, no Docker, no systemd for MVP.
- uvicorn runs inside a `tmux` session: `uvicorn main:app --host 0.0.0.0 --port 8000`.
- Frontend uses Tailwind via CDN (no npm build step).
- `marked.js` via CDN for markdown rendering.

### Sample Project

- A minimal FastAPI todo app (~8 files) committed to the repo under `samples/todo-app/`.
- "Try with sample project" button on the upload page POSTs to `/upload-sample`. Server zips the sample folder on-the-fly and runs it through the same pipeline as a regular upload.
- Live generation — not pre-baked output. The demo is genuine.

## Build Order

### Phase 1 — Foundation (~1.5 hours)
- **1a (20 min):** Project scaffold — `main.py`, `templates/`, `static/`, FastAPI init, Jinja2, Tailwind via CDN. Gate: blank page serves.
- **1b (30 min):** Upload page HTML — file input, drag-drop zone, Quick/Comprehensive radio, submit. Gate: page renders.
- **1c (40 min):** Upload endpoint — type validation, 50MB check, UUID session, save to `/tmp/`, extract zip (with try/except). Gate: upload a zip, verify extraction in `/tmp/`.

### Phase 2 — File Scanner (~45 min)
- **2a (25 min):** Directory walker + universal ignore list + binary file detection. Gate: clean source file list from a sample zip.
- **2b (20 min):** Section→file mapping via path patterns. Save `mapping.json`. Gate: correct mapping printed from sample project.

### Phase 3 — DeepSeek + SSE, the critical phase (~3 hours)
- **3a (20 min):** DeepSeek async client via `httpx`, API key from env, non-streaming test call. Gate: response in terminal.
- **3b (90 min):** SSE endpoint + streaming for README section only. HTMX SSE extension wired up. Gate: tokens appear character-by-character in browser. **Do not advance until this works end-to-end.**
- **3c (60 min):** All 5 sections with section-specific prompts, skeleton extractor, `section-start`/`section-complete` SSE events, frontend progress indicator.

### Phase 4 — Preview Page (~1.5 hours)
- **4a (45 min):** Jinja2 preview template, 5 section cards with stable IDs, `marked.js` rendering, progress indicator driven by SSE events.
- **4b (30 min):** Edit + Save flow — textarea toggle, `POST /edit`, HTMX card swap, unsaved indicator.
- **4c (30 min):** Regenerate flow — per-section SSE stream targeted at one card, other cards untouched.

### Phase 5 — Output (~50 min)
- **5a (30 min):** MkDocs `mkdocs.yml` generation + `subprocess.run` build. Gate: `site/` folder with HTML output.
- **5b (20 min):** Download endpoint — zip creation, `FileResponse`. Gate: download and open working HTML site.

### Phase 6 — Polish (~1.5 hours)
- **6a (20 min):** Sample project button — bundle todo app, `/upload-sample` endpoint.
- **6b (20 min):** Error states — oversized file, wrong type, DeepSeek API failure with retry button.
- **6c (50 min):** Tailwind UI polish — upload hero, generation progress screen, section cards. Do this last.

### Phase 7 — Deploy + Record (~1 hour)
- **7a (30 min):** VPS deployment — `git clone`, `pip install`, set `DEEPSEEK_API_KEY`, run uvicorn in tmux. Test end-to-end on VPS URL.
- **7b (30 min):** Record demo video using sample project. Show: upload → streaming generation → preview → edit → regenerate → download → open HTML site. Max 3 minutes.

## Testing Decisions

Given the 24-hour solo build window, automated tests are not part of the MVP. Manual testing gates are embedded in the build order above — each phase has an explicit "Gate" condition that must pass before moving on.

The highest-risk integration point (Phase 3b: SSE streaming + DeepSeek) should be manually tested with a real DeepSeek API call on a small file before expanding to the full pipeline. If this step fails, nothing else matters.

Post-hackathon, the modules most worth unit-testing in isolation are:
- The file scanner and ignore list (pure function, deterministic input/output)
- The skeleton extractor (pure function, testable against known files)
- The section→file mapper (pure function, pattern matching logic)

Good tests for these would assert on the file list produced from a fixture zip, not on the generated documentation content (which is non-deterministic).

## Out of Scope

- GitHub URL integration (fetch repos directly without manual download)
- FilePond / Uppy upload UI
- User accounts or persistent storage
- Custom MkDocs themes or colour scheme selection
- Live collaborative editing
- Auto-deployment to GitHub Pages or Vercel
- Programmatic API access
- Monorepo support (multiple languages in one project)
- Support for projects exceeding 50MB compressed
